# Chapter 10 - Garbage Collection (GC) ⭐⭐⭐⭐⭐

---

# 1. Why do we need Garbage Collection?

Let's start from the basic problem.

In languages like C/C++:

```cpp
User* user = new User();
```

Developer manually allocates memory.

Later:

```cpp
delete user;
```

Developer must free memory.

If they forget:

```text
Memory allocated

↓

No reference

↓

Memory never released

↓

Memory Leak
```

---

Java solves this problem.

In Java:

```java
User user = new User();
```

The JVM allocates memory.

When the object is no longer needed:

```text
Object created

↓

Used by application

↓

No references exist

↓

JVM removes it automatically
```

This automatic memory cleanup is:

> **Garbage Collection**

---

# Definition (Interview)

**Garbage Collection is the JVM process of automatically identifying and reclaiming memory occupied by objects that are no longer reachable by the application.**

Important words:

* Automatically
* Unreachable objects
* Reclaim memory

---

# Where does GC work?

Very important.

GC mainly works on the:

```text
Heap Memory
```

Recall our Runtime Data Areas:

```text
JVM Memory

+-----------------------+

Heap
   |
   |
   | <-- Garbage Collection happens here

+-----------------------+

Java Stack

+-----------------------+

Metaspace

+-----------------------+
```

GC does **not** clean:

* Java Stack frames
* CPU registers
* Local variables directly

It manages Heap objects.

---

# How does JVM know an object is garbage?

This is the most important concept.

The JVM does not ask:

> "Was this object used recently?"

Instead, it asks:

> "Can this object still be reached from a live reference?"

---

# Reachability Concept ⭐⭐⭐⭐⭐

Example:

```java
public void createUser() {

    User user = new User();

}
```

Memory:

```text
Stack

user
 |
 |
 ▼

Heap

+-------------+
| User Object |
+-------------+
```

The object is reachable.

It is alive.

---

Now after method finishes:

```text
Stack

(no user reference)


Heap

+-------------+
| User Object |
+-------------+
```

No path exists from the application to this object.

It becomes:

```text
Unreachable Object

↓

Eligible for GC
```

---

# GC Root Concept ⭐⭐⭐⭐⭐

The JVM starts checking from special references called:

> **GC Roots**

Examples:

* Active thread stack variables
* Static variables
* JNI references
* JVM internal references

The GC asks:

"Can I reach this object starting from a GC Root?"

---

Example:

```java
class Main {

    static User user = new User();

}
```

Memory:

```text
GC Root

Static Variable
      |
      |
      ▼

User Object
```

The object is reachable.

GC cannot remove it.

---

Now:

```java
user = null;
```

Memory:

```text
GC Root

Static Variable
      |
      X


User Object
```

No path.

Eligible for GC.

---

# Important Interview Point

Eligible for GC ≠ Immediately Deleted

This is a common question.

Wrong:

> "When object becomes unreachable, JVM immediately removes it."

Correct:

> "When object becomes unreachable, it becomes eligible for garbage collection. The JVM decides when to actually perform GC."

---

# Why doesn't JVM run GC continuously?

Because GC itself consumes CPU.

Example:

```text
Application Threads

       +
       |
       v

Garbage Collector

       |
       v

CPU Usage
```

If GC runs all the time:

* Application becomes slower.
* CPU is wasted cleaning memory.

So JVM uses intelligent algorithms to decide:

* When to run GC
* Which objects to clean
* How much memory to reclaim

# Chapter 10.1 - Heap Generations ⭐⭐⭐⭐⭐

---

# First Question

Suppose a Java application is running.

It creates millions of objects:

```java
User user = new User();
Order order = new Order();
Payment payment = new Payment();
```

Some objects:

* Live for milliseconds.
* Some live for minutes.
* Some live for the entire application lifetime.

Example:

```text
Temporary Object

Request DTO
↓
Used during API call
↓
Discarded


Long-lived Object

Database Connection Pool
↓
Lives for application lifetime
```

The JVM noticed an important pattern:

> **Most objects die young.**

This observation is the foundation of Generational GC.

---

# Generational Hypothesis

**Interview Definition**

The Generational Hypothesis states:

> Most newly created objects have a short lifetime, and objects that survive longer are likely to continue living.

Therefore, instead of treating all objects equally, JVM divides Heap into generations.

---

# Heap Structure

Traditional JVM Heap:

```text
                 Heap

        +--------------------+

        | Young Generation   |
        |                    |
        |  Eden              |
        |  Survivor S0       |
        |  Survivor S1       |

        +--------------------+

        | Old Generation     |

        +--------------------+
```

---

# Why divide Heap?

Without generations:

```text
Heap

Object 1
Object 2
Object 3
Object 4
...
Object 1 million
```

Every GC would need to scan everything.

Very expensive.

---

With generations:

```text
Young Generation

Mostly new objects

↓

Frequent GC


Old Generation

Long-lived objects

↓

Less frequent GC
```

The JVM focuses where garbage is most likely.

---

# Young Generation ⭐⭐⭐⭐⭐

The Young Generation stores:

> Newly created objects.

Example:

```java
User user = new User();
```

Initially:

```text
Young Generation

+-------------+
| User Object |
+-------------+
```

Most objects die here.

---

# Young Generation Structure

Young Generation has three parts:

```text
Young Generation

+----------------+
| Eden           |
+----------------+

+----------------+
| Survivor S0    |
+----------------+

+----------------+
| Survivor S1    |
+----------------+
```

---

# 1. Eden Space

When you create an object:

```java
User user = new User();
```

It goes into:

```text
Eden
```

Example:

```text
Eden

User
Order
Payment
Invoice
```

Most objects stay here briefly.

---

# 2. Survivor Spaces

After Eden becomes full:

A **Minor GC** happens.

Live objects are moved to Survivor space.

Example:

Before GC:

```text
Eden

User A   ❌
User B   ✅
User C   ❌
User D   ✅
```

After GC:

```text
Survivor S0

User B
User D
```

Dead objects are removed.

---

# Survivor Spaces S0 and S1

Why two survivor spaces?

Because JVM uses copying.

Structure:

```text
Before GC

Eden        S0        S1

Objects     Live      Empty


After GC

Empty       Live      Empty
Eden
```

Then next cycle:

```text
Eden        S0        S1

Objects     Empty     Live
```

They keep swapping roles.

---

# Object Promotion

The next important concept:

> How does an object move to Old Generation?

Example:

```text
Object Created

↓

Eden

↓

Minor GC

↓

Survivor S0

↓

Survive many GC cycles

↓

Old Generation
```

This movement is called:

> **Promotion**

---

# Old Generation ⭐⭐⭐⭐⭐

Old Generation stores:

> Long-lived objects.

Examples:

```java
Application Configuration

Cache Objects

Connection Pools

Singleton Objects
```

These objects survive multiple GC cycles.

---

# Why separate Old Generation?

Because old objects are less likely to become garbage.

Imagine:

```text
Young Generation

10 million objects

↓

Most die quickly


Old Generation

10000 objects

↓

Mostly alive
```

Running GC frequently on Old Generation would waste time.

---

```text
        |
        v

     Eden

        |
        |
   Minor GC

        |
        v

        |
        |
 Survive multiple GC cycles

        |
        v

        |
        |

        |
        v

 Removed
```

## Q1. Why does JVM divide Heap into generations?

**Young Generation**

When an object survives enough Minor GC cycles, it gets promoted to Old Generation.

# Interview Questions

## Q1. What happens when Eden becomes full?

When Eden becomes full, JVM triggers a Minor GC. Application threads are paused, live objects are identified, copied to Survivor space, and unreachable objects are reclaimed.

---

## Q2. Why are Survivor spaces needed?

Survivor spaces allow JVM to keep objects that are still alive after Minor GC and track their age before promoting them to Old Generation.

---

## Q3. Why does JVM use two Survivor spaces?

Because GC uses a copying approach.

Objects are copied from one survivor space to another, allowing compact memory without fragmentation.

---

## Q4. What is object promotion?

Promotion is the process where long-lived objects move from Young Generation to Old Generation after surviving multiple Minor GC cycles.

---

## Q5. Is Minor GC always a small pause?

Usually yes, because it only processes Young Generation, but pause time depends on:

* Number of live objects
* Heap size
* GC algorithm
* Application allocation rate

---

# Good to Know (Optional)

## 1. Does Minor GC always stop the whole application?

Traditional collectors generally use Stop-The-World pauses.

Modern collectors try to reduce pause impact using concurrent phases.

---

## 2. Does GC immediately free memory to OS?

Not necessarily.

GC reclaims memory inside the JVM Heap.

The JVM may keep that memory available for future allocations instead of returning it immediately to the operating system.

---

## 3. Can objects skip Survivor space?

Yes.

Under certain conditions, large objects or JVM heuristics may directly promote objects to Old Generation.

* Usually faster.

**Major GC**

* Mainly collects Old Generation.
* Happens less frequently.
* Usually more expensive.

---

## Q2. What is Full GC?

Full GC collects the entire JVM memory area including:

* Young Generation
* Old Generation
* Metaspace

---

## Q3. Why is Full GC expensive?

Because it scans and processes a much larger memory area compared to Minor GC.

---

## Q4. Does Major GC always mean Full GC?

No.

Traditionally:

```
Major GC → Old Generation
Full GC → Entire Heap
```

But terminology varies between collectors.

# Chapter 10.4 - Garbage Collection Algorithms ⭐⭐⭐⭐⭐

---

# Why do we need GC Algorithms?

Suppose Heap looks like this:

```text
Heap

+----+----+----+----+----+
| A  | B  | C  | D  | E  |
+----+----+----+----+----+

A = alive object
B = garbage
C = alive object
D = garbage
E = alive object
```

The JVM needs to:

1. Find garbage objects.
2. Remove them.
3. Organize remaining memory.

Different algorithms solve this differently.

---

# Main GC Algorithms

The important ones:

```text
Garbage Collection Algorithms

├── Mark and Sweep
├── Mark and Compact
├── Copying Algorithm
└── Generational Collection
```

---

# 1. Mark and Sweep ⭐⭐⭐⭐⭐

This is the simplest GC algorithm.

It works in two phases:

```text
Mark

↓

Sweep
```

---

# Phase 1: Mark

The JVM identifies reachable objects.

Example:

```text
Heap

+----+----+----+----+
| A  | B  | C  | D  |
+----+----+----+----+

A = reachable
B = unreachable
C = reachable
D = unreachable
```

GC marks:

```text
A  ✓
B  X
C  ✓
D  X
```

---

# Phase 2: Sweep

Now JVM removes unmarked objects.

Before:

```text
+----+----+----+----+
| A  | B  | C  | D  |
+----+----+----+----+
```

After:

```text
+----+----+----+----+
| A  |    | C  |    |
+----+----+----+----+
```

Memory is reclaimed.

---

# Problem with Mark and Sweep

The biggest issue:

> Fragmentation

Example:

```text
Before:

+----+----+----+----+----+
| A  | B  | C  | D  | E  |
+----+----+----+----+----+

Remove B and D:

+----+----+----+----+----+
| A  |    | C  |    | E  |
+----+----+----+----+----+
```

Free memory exists.

But it is scattered.

---

Imagine:

You have:

```text
10 MB free memory
```

but split like:

```text
2 MB + 3 MB + 5 MB
```

You cannot allocate:

```text
8 MB object
```

because there is no continuous block.

This is:

> Memory Fragmentation

---

# 2. Mark and Compact ⭐⭐⭐⭐⭐

Mark and Compact solves fragmentation.

Two phases:

```text
Mark

↓

Compact
```

---

# Phase 1: Mark

Same as before.

```text
Heap

A ✓
B X
C ✓
D X
E ✓
```

---

# Phase 2: Compact

Instead of leaving holes,

move live objects together.

Before:

```text
+----+----+----+----+----+
| A  |    | C  |    | E  |
+----+----+----+----+----+
```

After:

```text
+----+----+----+----+----+
| A  | C  | E  |    |    |
+----+----+----+----+----+
```

Now free memory is continuous.

---

# Benefit

No fragmentation.

Large objects can be allocated easily.

---

# Cost

Moving objects is expensive.

Why?

Because all references must be updated.

Example:

Before:

```text
User reference

   |
   v

Object at address 1000
```

After moving:

```text
User reference

   |
   v

Object at address 5000
```

The JVM must update references.

---

# 3. Copying Algorithm ⭐⭐⭐⭐

Mostly used in Young Generation.

Idea:

Instead of deleting garbage,

copy live objects to another area.

Example:

Before:

```text
From Space

+----+----+----+----+
| A  | B  | C  | D  |
+----+----+----+----+

A,C alive
B,D garbage
```

Copy:

```text
To Space

+----+----+
| A  | C  |
+----+----+
```

Then discard old space completely.

---

# Why is Copying Fast?

Because no need to individually remove objects.

Just:

```text
Copy alive objects

↓

Throw away old region
```

Very efficient.

---

# Problem with Copying

Requires extra memory.

Example:

```text
Heap

50% From Space

50% To Space
```

You need additional space for copying.

---

# Where do we use Copying?

Young Generation.

Why?

Because:

> Most young objects die quickly.

Example:

```text
Eden

1 million objects

↓

Minor GC

900,000 garbage

100,000 survive
```

Copying only moves the small surviving set.

---

# 4. Generational Collection ⭐⭐⭐⭐⭐

This is what modern Java GC is based on.

It combines ideas:

```text
Young Generation

↓

Copying Algorithm


Old Generation

↓

Mark-Sweep / Mark-Compact
```

---

# Why Different Algorithms?

Because object behaviour is different.

Young objects:

```text
Created

↓

Die quickly
```

Copying works well.

---

Old objects:

```text
Live longer

↓

Need different strategy
```

Mark-Compact works better.

---

# Complete Picture

```text
                 Heap


        Young Generation

              |
              |
              v

       Copying Collector


              |
              |
              v


        Old Generation

              |
              |
              v

     Mark-Sweep / Compact
```

---

# Interview Comparison

| Algorithm    | Advantage                       | Problem               |
| ------------ | ------------------------------- | --------------------- |
| Mark-Sweep   | Simple                          | Fragmentation         |
| Mark-Compact | No fragmentation                | Object movement cost  |
| Copying      | Very fast                       | Requires extra memory |
| Generational | Efficient for real applications | More complex          |

# Interview Questions

## Q1. Explain Mark and Sweep.

Mark and Sweep identifies reachable objects during the mark phase and removes unreachable objects during the sweep phase.

---

## Q2. What is fragmentation?

Fragmentation happens when free memory exists but is scattered into small non-contiguous blocks, preventing large allocations.

---

## Q3. Difference between Mark-Sweep and Mark-Compact?

Mark-Sweep removes garbage but leaves memory gaps.

Mark-Compact moves live objects together after removing garbage, eliminating fragmentation.

---

## Q4. Why is copying algorithm used in Young Generation?

Because most young objects die quickly, so only a small number of objects need to be copied.

# Chapter 10.6 - G1 Garbage Collector Deep Dive ⭐⭐⭐⭐⭐

---

# 1. Why was G1 introduced?

Let's first understand the problem.

Before G1:

```text
Heap

+----------------+
| Young          |
+----------------+
| Old            |
+----------------+
```

Traditional collectors:

* Serial
* Parallel
* CMS

worked with fixed generations.

Problem:

Large heaps became difficult.

Example:

```text
Heap = 64 GB

Old Generation = 50 GB
```

A Full GC could take several seconds.

For backend systems:

```
Request latency:

100 ms normally

↓

GC pause

↓

5 seconds
```

This is unacceptable.

---

# G1 Goal

G1 stands for:

> **Garbage First**

Its goal:

> Provide predictable pause times while handling large heaps.

---

# Main Idea of G1

Traditional GC:

```text
Heap

Young Generation

Old Generation
```

G1:

```text
Heap divided into many small regions
```

Example:

```text
+----+----+----+----+
| R1 | R2 | R3 | R4 |
+----+----+----+----+
| R5 | R6 | R7 | R8 |
+----+----+----+----+
| R9 |R10 |R11 |R12 |
+----+----+----+----+
```

Each region can represent:

* Eden
* Survivor
* Old

---

# 2. What is a G1 Region?

A region is a small chunk of heap memory.

Instead of:

```
One large Young area
One large Old area
```

G1 manages:

```
Many small independent regions
```

Example:

```
Region 1 → Eden
Region 2 → Eden
Region 3 → Survivor
Region 4 → Old
Region 5 → Old
```

The JVM dynamically changes region roles.

---

# Why are regions useful?

Because G1 can choose where to collect.

Example:

Heap:

```
Region A

90% garbage


Region B

20% garbage


Region C

5% garbage
```

A traditional collector may scan everything.

G1 says:

```
Collect Region A first
```

because it gives maximum memory recovery.

Hence:

```
Garbage First
```

---

# 3. G1 Heap Layout

Example:

```
                 G1 Heap


+------+ +------+ +------+
| Eden | | Eden | | Old  |
+------+ +------+ +------+

+------+ +------+ +------+
|Surv. | | Old  | | Old  |
+------+ +------+ +------+

+------+ +------+ +------+
| Eden | | Old  | | Free |
+------+ +------+ +------+
```

There is no fixed:

```
Young = first 30%

Old = remaining
```

Instead:

```
Regions are assigned dynamically.
```

Similar concept to Minor GC.

Objects are created:

```

↓

Eden Region
```

```
Eden Regions

+--------+
| Object |
| Object |
| Object |
+--------+
```

When Eden fills:

```

```

```
Survivor Regions
```

Same idea as traditional generational GC.

# 4. Memory Leak in Java ⭐⭐⭐⭐⭐

A common misconception:

> "Java has Garbage Collection, so Java cannot have memory leaks."

Wrong.

Java can have memory leaks.

---

# What is a Memory Leak?

**Definition (Interview)**

A memory leak occurs when objects are no longer required by the application but are still reachable through references, preventing Garbage Collection.

Important:

Object is useless.

But JVM thinks:

"Something still references it."

---

# Example 1: Static Collection Leak

```java
public class UserCache {

    private static List<User> users =
            new ArrayList<>();


    public void add(User user) {

        users.add(user);

    }
}
```

Problem:

Static variable lives until JVM shutdown.

Memory:

```
GC Root

   |
   |
Static List

   |
   |
Millions of User Objects
```

GC says:

"They are reachable."

So:

```
No GC
```

Memory keeps growing.

---

# Example 2: Cache Without Eviction

Bad:

```java
Map<String, User> cache =
        new HashMap<>();
```

Adding:

```
user1
user2
user3
...
millions
```

No removal.

Result:

```
Heap Growth

↓

Old Generation Full

↓

Full GC

↓

OutOfMemoryError
```

---

# Example 3: ThreadLocal Leak ⭐⭐⭐⭐

Common in backend systems.

Example:

```java
ThreadLocal<User> user =
        new ThreadLocal<>();
```

Thread pools reuse threads.

If cleanup is missing:

```java
thread

 |
 ThreadLocalMap

 |
 User Object
```

The object may stay longer than expected.
