Excellent. This is one of the **most important JVM topics**. Once you understand bytecode, you'll finally understand what the JVM is actually executing.

Most developers know:

or

# Chapter 5 - Bytecode

# The Big Picture

Let's recall where we are.

```text
                Main.java
                    │
                    ▼
                 javac
                    │
                    ▼
               Main.class
                    │
                    ▼
                JVM loads it
                    │
                    ▼
          JVM executes Bytecode
```

Notice something.

The JVM **does NOT execute Java code**.

It executes **Bytecode**.

Java source code is only for developers.

The JVM has no idea what `public`, `class`, `for`, or `if` are.

It only understands **Bytecode Instructions**.

---

# What is Bytecode?

**Definition**

Bytecode is the **platform-independent intermediate instruction set** generated by the Java compiler (`javac`) from Java source code.

Think of it as a language understood by **all JVM implementations**.

```text
Java Source

↓

javac

↓

Bytecode

↓

HotSpot JVM

or

↓

OpenJ9 JVM

or

↓

GraalVM
```

Every JVM understands the same bytecode because it follows the **JVM Specification**.

---

# Why was Bytecode introduced?

This is one of the favourite interview questions.

Imagine Java didn't have bytecode.

```text
Main.java

↓

javac

↓

Windows Machine Code
```

Now try running it on Linux.

Impossible.

Now compile again.

```text
Main.java

↓

Linux Compiler

↓

Linux Machine Code
```

Now compile again for macOS.

```text
Main.java

↓

macOS Compiler

↓

macOS Machine Code
```

Every platform needs a different compiler.

Exactly how C/C++ works.

---

Java solved this problem.

Instead of compiling to machine code,

it compiles to **Bytecode**.

```text
                 Main.java
                      │
                  javac
                      │
             Platform Independent
                  Bytecode
                      │
      ┌───────────────┼───────────────┐
      ▼               ▼               ▼
 HotSpot          OpenJ9          GraalVM
 (Windows)        (Linux)         (macOS)
      │               │               │
      ▼               ▼               ▼
Machine Code     Machine Code     Machine Code
```

Now the same `.class` file runs everywhere.

This is the reason Java became famous for:

> **Write Once, Run Anywhere (WORA)**

---

# Why not compile directly to Machine Code?

Good interview question.

Suppose Java compiled directly to machine code.

Problems:

```text
Need different compiler

↓

Different executable

↓

Different optimisations

↓

Platform dependency

↓

No portability
```

Bytecode solves all of these.

# What does Bytecode look like?

Suppose we have

```java
public class Main {

    public static void main(String[] args) {

        int a = 10;
        int b = 20;
        int c = a + b;

    }

}
```

We don't get

```text
MOV R1, R2
ADD R1, R3
```

Instead,

we get JVM instructions.

Example:

```text
bipush 10
istore_1

bipush 20
istore_2

iload_1
iload_2
iadd
istore_3

return
```

These are called **Bytecode Instructions** or **Opcodes**.

---

# Why is it called Bytecode?

Historically, many JVM instructions were encoded using **one-byte operation codes (opcodes)**.

Example

```text
Opcode

0x60

↓

iadd
```

Another

```text
0x1a

↓

iload_0
```

Another

```text
0xac

↓

ireturn
```

Hence the name:

**Byte + Code = Bytecode**

Although some instructions have additional operands, the operation itself is identified by an opcode.

# Bytecode is NOT Machine Code

This interview question appears surprisingly often.

| Bytecode                    | Machine Code                        |
| --------------------------- | ----------------------------------- |
| Executed by JVM             | Executed directly by CPU            |
| Platform Independent        | Platform Dependent                  |
| Generated by `javac`        | Generated by JIT or native compiler |
| Same on Windows/Linux/macOS | Different for each CPU architecture |

Meaning:

# Does Bytecode Contain Variable Names?

Interesting interview question.

Example

```java
int salary = 100;
```

The JVM doesn't care about the variable name.

It mostly works with **local variable slots**.

Instead of

```text
salary
```

it uses something like

```text
slot 1
```

Variable names are primarily debugging information and may not even be present unless compiled with the appropriate debug information.

---

# One Java Statement = Multiple Bytecode Instructions

Developers often think

```java
int c = a + b;
```

becomes

```text
ADD
```

Wrong.

It becomes several instructions.

```text
Load a

↓

Load b

↓

Add

↓

Store result
```

Which is approximately:

```text
iload_1

iload_2

iadd

istore_3
```

The JVM executes them one by one (or compiles them later via JIT).

---

# Important Point

The JVM is a **stack-based virtual machine**.

Notice:

```text
iload_1

↓

Operand Stack

↓

iload_2

↓

Operand Stack

↓

iadd

↓

Operand Stack

↓

istore_3
```

There are **no general-purpose registers** exposed in JVM bytecode.

Everything operates through the **operand stack**.

This is a huge interview topic, and we'll cover it separately because understanding the operand stack is essential for reading bytecode.

# Common Interview Questions

## Q1. What is Bytecode?

**Answer**

Bytecode is the platform-independent intermediate instruction set generated by the Java compiler (`javac`). It is stored in `.class` files and executed by any JVM implementation that conforms to the JVM Specification.

---

## Q2. Why doesn't Java compile directly to Machine Code?

Because machine code is platform-specific. By compiling to platform-independent bytecode, Java allows the same `.class` file to run on any operating system with a compatible JVM. The JVM later interprets or JIT-compiles the bytecode into native machine code for the host platform.

---

## Q3. Is Bytecode human-readable?

Not directly. The `.class` file is a binary format. Tools like `javap` can disassemble it into a readable form showing bytecode instructions.

---

## Q4. Can languages other than Java generate Bytecode?

Yes.

Any language targeting the JVM can generate standard JVM bytecode, including:

* Kotlin
* Scala
* Groovy
* Clojure
* JRuby
* Jython (historically)

The JVM doesn't know whether the bytecode originated from Java or another JVM language—it simply executes valid bytecode.
