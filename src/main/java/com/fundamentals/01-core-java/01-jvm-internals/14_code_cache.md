# Chapter 9.5 - Code Cache ⭐⭐⭐

---

# First Question

We learned:

```text
Bytecode

↓

JIT Compiler

↓

Machine Code
```

Question:

**Where does the JVM store this machine code?**

It obviously cannot go back into the `.class` file.

It doesn't belong in the Heap because the Heap stores **objects**.

So where does it go?

Answer:

> **Code Cache**

---

# What is the Code Cache?

**Definition (Interview)**

The **Code Cache** is a special memory area inside the JVM where the **JIT Compiler stores compiled native machine code**.

Think of it as:

> **A cache of compiled machine code ready for direct CPU execution.**

---

# Why do we need a Code Cache?

Imagine a hot method.

```java
static int add(int a, int b) {
    return a + b;
}
```

Suppose the JVM compiles it.

Without a Code Cache,

every execution would look like:

```text
Hot Method

↓

JIT Compiler

↓

Machine Code

↓

Execute

↓

Throw Away

↓

Compile Again
```

That would be extremely inefficient.

Instead,

the JVM compiles the method **once** and stores the compiled result.

---

# Execution Flow

```text
Bytecode

↓

Interpreter

↓

Hot Method

↓

JIT Compiler

↓

Code Cache

↓

CPU Executes Machine Code
```

Future calls simply jump to the compiled code.

---

# Visualisation

```text
                    JVM

+----------------------------------+

Heap
(Object Instances)

+----------------------------------+

Metaspace
(Class Metadata)

+----------------------------------+

Code Cache
(Compiled Machine Code)

add()

login()

calculateTax()

processOrder()

+----------------------------------+
```

Notice:

The Code Cache stores **machine instructions**, **not Java objects**.

---

# What is Stored in the Code Cache?

Conceptually,

```text
Code Cache

├── Machine Code
├── Optimised Methods
├── Compiled Loops
└── JIT Metadata
```

For interviews,

remember only:

> **Compiled native code produced by the JIT Compiler.**

---

# Why is it called a Cache?

A cache stores data that is expensive to recreate.

Example:

```text
Machine Code

↓

Expensive Compilation

↓

Store Once

↓

Reuse Many Times
```

Instead of recompiling,

the JVM reuses the existing compiled code.

Hence the name:

**Code Cache**

---

# What happens during execution?

Suppose

```java
add(10,20);
```

Initially,

```text
Interpreter

↓

Execute Bytecode
```

After the method becomes hot,

```text
Interpreter

↓

JIT Compiler

↓

Code Cache
```

Future executions become:

```text
Method Call

↓

Code Cache

↓

Machine Code

↓

CPU
```

The Interpreter is bypassed for that compiled version.

---

# What if the Code Cache becomes Full?

Another interview question.

Suppose

```text
Code Cache

██████████████████

100% Full
```

Now the JIT Compiler cannot store additional compiled methods.

Possible consequences:

* Fewer methods can be JIT-compiled.
* Some methods continue running in interpreted mode.
* Application performance may decrease.
* The JVM can log warnings such as:

```text
CodeCache is full. Compiler has been disabled.
```

This is uncommon in typical applications but can occur in large, long-running systems.

---

# Can Code Cache be Configured?

Yes.

HotSpot provides JVM options to control the size of the Code Cache.

For interviews,

you don't need to memorise JVM flags.

Just know:

> **The Code Cache has a finite size and can be tuned if necessary.**

# Interview Questions

### Q1. What is the Code Cache?

The Code Cache is a JVM memory area that stores **native machine code generated by the JIT Compiler**.

---

### Q2. Why do we need the Code Cache?

To avoid recompiling the same hot methods repeatedly. The JVM compiles them once and reuses the compiled machine code.

---

### Q3. Does the Code Cache store Java objects?

No.

The Heap stores Java objects.

The Code Cache stores **compiled machine instructions**.

---

### Q4. What happens if the Code Cache is full?

The JVM may stop compiling additional methods, causing more code to run in interpreted mode and potentially reducing performance.

# Good to Know (Optional)

### 1. Is the Code Cache defined by the JVM Specification?

No.

The **JVM Specification** does not define a Code Cache.

It is an implementation detail of JVMs that use JIT compilation, such as **HotSpot**.

---

### 2. Is the Code Cache Garbage Collected?

In a sense, yes.

When compiled code becomes invalid (for example, after **deoptimisation**) or is no longer useful, the JVM can reclaim space in the Code Cache.

You don't need to understand the reclamation algorithms for interviews.

---

### 3. Does every JVM have a Code Cache?

Only JVM implementations that compile bytecode to native machine code need an equivalent mechanism.

A purely interpreted JVM would not need one.

# Runtime Optimisations - Final Boundary

## 1. Method Inlining ⭐⭐⭐⭐⭐

**Keep (high priority, but short)**

Why?

Because it is directly connected to JIT and commonly asked.

Example:

```java
public int calculate() {
    return add(10,20);
}

private int add(int a, int b) {
    return a + b;
}
```

Normally:

```text
calculate()

↓

call add()

↓

return result
```

JIT may transform it into:

```java
calculate()

↓

return 10 + 20
```

The method call overhead is removed.

Know:

* What it is
* Why JIT does it
* Benefit

Stop there.

---

## 2. Escape Analysis ⭐⭐⭐⭐

**Keep (short)**

Reason:

It connects with Heap and Object Allocation.

Example:

```java
public void process() {

    User user = new User();

}
```

Question:

Does this object need Heap allocation?

If the JVM proves:

> "This object never leaves this method"

it may optimize it.

Possible optimizations:

* Stack allocation (conceptually)
* Scalar replacement
* Lock elimination

For interviews:

Just know the idea.

---

## 3. Dead Code Elimination ⭐⭐⭐

**Skip deep.**

Just know:

The JIT removes code that never affects the output.

Example:

```java
int x = 10;

x = 20;

System.out.println(x);
```

The JVM can remove unnecessary operations.

---

## 4. Loop Optimisation ⭐⭐⭐

**Skip deep.**

Just know:

Loops are hot areas, so JIT applies optimisations.

Examples:

* Loop unrolling
* Removing unnecessary checks

No need to study algorithms.

---

## 5. Constant Folding ⭐⭐⭐

**Skip deep.**

Simple concept:

Compile-time calculations can be done early.

Example:

```java
int result = 10 * 20;
```

can become:

```java
int result = 200;
```
